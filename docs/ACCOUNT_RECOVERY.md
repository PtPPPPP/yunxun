# 密码与账号恢复

## 用户怎样保管账号

正式账号在「账号安全」输入原密码后可以修改密码，也可以生成一次性恢复码。新设置的密码为 8–64 位，不能全为空格；已有较短密码仍可登录，再按新要求修改。

恢复码由用户本人离线保管，例如存入本人密码管理器或写下妥善保存。它相当于重置账号密码的钥匙，不要交给他人。页面只在生成成功时展示一次；关闭、刷新或离开后无法再次查看。服务器不保留原文，也不提供再次查询入口。重新生成后旧码立即失效，以最后收到的恢复码为准。若生成响应中断，可以使用当前密码重新生成。

忘记密码时，从登录页选择「用恢复码重置密码」，输入用户名、恢复码和新密码。用户名只是定位账号，必须有正确恢复码才能重置。成功使用一次后恢复码失效。

修改密码、恢复码重置或本机辅助重置都会同时撤销该账号全部会话和旧恢复码，包括当前浏览器与其他设备的 Cookie、Bearer 会话。成功后重新登录，再生成新的恢复码。业务数据、用户 ID 和关联关系保留。已经进入执行的业务请求不会强制中断，之后的请求须重新认证。

## 丢失凭据怎么办

没有提前生成恢复码，或密码与恢复码都丢失时，请联系管理这台电脑的部署者。部署者必须在线下独立核验账号所有者身份后，才能使用本机管理命令设置临时密码；不能只根据用户名或显示名称认定所有权。用户收到临时密码后应立即修改，再自行生成恢复码。软件不会代替部署者判断线下身份证据，也没有短信、邮件或公开信息找回功能。

部署者无法可靠核验身份、或无人拥有部署电脑的管理权限时，本版本不能恢复账号。数据库文件本身丢失也不能靠恢复码恢复业务数据，需要独立的数据库备份。

## 访客和历史账号

- 明确标记的访客不能管理密码或使用恢复码，须先在有效访客会话中「保存账号」。访客没有设置可供本人使用的登录密码；丢失会话后没有自助找回能力。本机命令也不会将访客擅自转为正式用户。
- 正式账号不自动生成恢复码。主动生成后才有自助恢复能力。
- Schema 10 之前无法可靠识别的历史账号继续按普通账号保留，不凭 `guest_` 前缀改变身份。有原密码的可登录后设置恢复码；没有凭据的只能走部署者线下核验，本机命令不批量转换账号。

## 部署者本机操作

在可信本机交互终端运行，明确指定**实际运行实例**所用的现有数据库绝对路径：

```powershell
python scripts/account_admin.py --database "C:\path\to\yunxun.db" --username farmer
```

先按备份流程备份，并确认数据库已由当前应用升级到当前版本 Schema 12。命令会显示目标文件和用户名，要求再次输入完整用户名确认，再隐藏输入两次新密码。不接受密码命令行参数、环境变量或管道输入，不自动创建数据库或替你迁移。取消、校验失败或事务失败不会部分修改账号；账号 ID、角色、显示名称及业务数据不变。

部署者的授权来自操作系统账号对数据库文件的访问权限。文件及备份应仅对可信部署者开放；能写数据库的人本就能修改所有账号，管理命令不能代替操作系统权限隔离。命令没有对应的无认证 HTTP 管理入口。

恢复数据库旧备份会同时恢复当时的密码摘要、恢复码摘要和会话摘要，可能使后来撤销的凭据再次有效。恢复后应按实际影响安排账号改密/本机重置、撤销旧凭据，再恢复使用；不要把数据库恢复等同于账号恢复。

## 实现边界

Schema 11 仅向 `users` 增加可空 `recovery_code_hash`，已有用户默认未启用恢复，保留既有业务和会话。恢复码由 `secrets.token_urlsafe(32)` 生成（256 位随机量），存储带独立域的 SHA-256 摘要；密码沿用现有加盐 PBKDF2。凭据替换、恢复码失效和全部 Token 删除在一个 SQLite 写事务中完成。登录签发 Token 时在写锁下复核密码摘要，避免旧密码登录与改密竞争后补发会话。

提交凭据只通过请求体，新恢复码仅通过生成响应体展示一次，成功响应禁止缓存，不写 URL、应用日志或浏览器持久存储。部署者不得额外开启请求体/响应体调试日志或把密码放进命令历史。局域网传输仍应使用受信任网络；本功能没有引入或验收公网 HTTPS/多实例部署能力。

原密码验证入口每账号 10 分钟最多 5 次；恢复入口每来源 IP 10 分钟最多 20 次、每规范化用户名 10 分钟最多 5 次，包含失败与成功尝试，并叠加既有认证限流。未知账号、访客、未生成、错误或已失效的恢复码返回相同提示和状态。429 附带等待时间。计数为当前单进程内存状态，进程重启会清空；不信任客户端转发 IP 头，不提供公网分布式防护保证。恶意针对某用户名可造成临时恢复限流，原密码登录与本机辅助恢复仍可用。
