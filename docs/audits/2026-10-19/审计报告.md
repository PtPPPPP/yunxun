## 已验证的问题

### F1 · P1：退出失败后仍保留有效会话，刷新会重新登录

- 位置：[App.tsx:194](../../../frontend/src/App.tsx#L194)，[auth.py:77](../../../backend/app/api/routes/auth.py#L77)、[auth.py:112](../../../backend/app/api/routes/auth.py#L112)。
- 触发：登录后令 `POST /api/auth/logout` 网络请求失败，点击退出，再刷新页面。
- 实测：页面先显示登录界面，但 `/api/me` 仍返回 **200**；刷新后自动进入原账号首页。
- 原因：`handleLogout` 忽略请求异常后清空 React 状态。实际凭据是 HttpOnly Cookie，需要服务端响应删除，同时撤销服务端会话；清空组件状态无法完成这两件事。
- 影响：用户以为已退出，在共用设备上后续使用者仍可能打开其账号。
- 最小修复方向：区分“本地隐藏资料”与“服务端退出已确认”，失败时明确提示并提供重试。若支持断网时本地退出，应保存一个不含凭据的退出待确认标记，阻止启动时静默恢复旧会话，并在恢复网络后完成撤销。仅靠前端删除 HttpOnly Cookie 不可行。
- 验收：覆盖请求未到服务端、服务端已撤销但响应丢失、正常退出三个分支；重新打开页面不得无提示恢复用户刚刚要求退出的账号。

### F2 · P2：旧账号保存姓名的迟到响应覆盖新账号的界面身份

- 位置：[App.tsx:175](../../../frontend/src/App.tsx#L175)。
- 触发：账号 A 保存显示名称，暂缓返回 PATCH 响应；退出 A，登录 B，再返回 A 的响应。
- 实测：页面姓名变为 A 的 `delayed-old-account`，但服务端 `/api/me` 仍是 B，B 的会话没有变化。
- 原因：保存设置成功后直接 `setUser(response.data.user)`，没有像地块等 Hook 一样检查请求所属账号/登录轮次。
- 影响：界面身份与实际请求身份不一致。后续操作实际作用于 B，用户却看到 A 的名称。**本次没有复现服务端越权，也不把它描述为认证绕过。**
- 最小修复方向：所有写入登录状态的异步入口统一检查会话轮次；退出和重新认证时递增轮次，迟到成功和错误响应都应忽略。先覆盖本处，随后检查 bootstrap、登录、升级和恢复入口，避免只靠开发者记得逐处加保护。
- 验收：A→退出、A→B、A→退出→再次登录 A，都不能被旧请求覆盖；不能仅比较用户 ID。

### F3 · P2：切换地块后，旧建议可以保存到新的地块

- 位置：[App.tsx:287](../../../frontend/src/App.tsx#L287)、[App.tsx:305](../../../frontend/src/App.tsx#L305)，[DecisionWorkspace.tsx](../../../frontend/src/components/DecisionWorkspace.tsx)。
- 触发：选择 A 玉米地并生成建议，切换到 B 番茄地，直接点击“把建议存为待办”。
- 实测：新待办关联 B，标题是“番茄：按今日建议安排农活”，备注却完整保留 A 的玉米建议。
- 原因：结果只保存一段字符串，保存操作读取当前选中的地块；修改地块和输入条件没有使旧结果失效。请求执行过程中输入也仍可修改。
- 最小修复方向：结果连同生成时的地块和输入快照保存，任务从该快照创建；或者输入一变就清空旧结果，并拒绝已经过期的请求响应。当前规模下这两个方案都比增加通用工作流系统简单。
- 验收：地块、作物、湿度等变化后旧结果不可被当成新结果保存；请求中切换地块、连续生成和保存也应保持对应关系。

### F4 · P2：创建地块与第一茬不在一个事务中

- 位置：[services/farm.py:159](../../../backend/app/services/farm.py#L159)，[repositories.py:314](../../../backend/app/repositories.py#L314)、[repositories.py:549](../../../backend/app/repositories.py#L549)。
- 触发：在第二步 `create_season` 注入 SQLite 写入异常。
- 实测：接口 **500**；地块数量从 **1 增为 2**；新增地块的 `active_season` 为 `null`。
- 原因：`create_plot` 与 `create_season` 各自创建连接并提交。第二步失败不能回滚第一步。
- 影响：界面报告失败，数据库却留下部分成功的数据；直接重试还可能产生重复地块。
- 最小修复方向：为“新建地块并建立第一茬”建立一个明确的数据库操作，两次 INSERT 共用同一连接与事务。此处不需要先引入通用 Unit of Work、ORM 或抽象仓储基类。
- 验收：第二次 INSERT 失败时两者均不存在；成功时两者同时存在。另行区分“事务成功但响应丢失”的重试问题，事务本身不解决后者。

### F5 · P2：修改茬次日期会制造已有台账无法通过自身校验的状态

- 位置：[services/farm.py:109](../../../backend/app/services/farm.py#L109)，[repositories.py:605](../../../backend/app/repositories.py#L605)，对照 [services/farm.py:298](../../../backend/app/services/farm.py#L298)。
- 触发：4 月 1 日开始的茬次已有 4 月 30 日施肥记录，把茬次开始日改到 6 月 1 日，再仅修改这条记录的费用。
- 实测：修改茬次返回 **200**；费用编辑返回 **422：作业日期不在所选茬次的起止日期内**。
- 原因：台账新增/编辑要求日期符合所属茬次，但修改茬次不检查已关联台账。
- 影响：原本有效的记录被动变为不合法状态，日期与归茬关系矛盾，普通编辑受阻；回收站恢复也可能被日期冲突阻止。
- 最小修复方向：在更新茬次的写事务里检查关联记录的日期范围。默认拒绝会造成冲突的修改，告诉用户影响条数及处理方式；若未来支持重新归茬，应作为明确的独立操作。兼容的地块编辑入口也要复用同一规则。
- 验收：起止日期变化、空日期、已有正常及回收站记录、兼容地块更新入口保持一致；不静默改动用户记录的日期或归属。

### F6 · P2：异步路由直接执行同步 SQLite，写锁阻塞整个服务事件循环

- 位置：[api/routes/farm.py:103](../../../backend/app/api/routes/farm.py#L103)，[core/database.py:29](../../../backend/app/core/database.py#L29)；认证路由也应一并检查同步数据库和密码计算。
- 触发：独立连接保持 SQLite 写事务 2.5 秒，同时请求新增地块，再并发请求不访问数据库的 `/health/live`。
- 实测首次结果：健康检查基线 **0.026 秒**，写锁期间 **2.109 秒**，两项请求最终均成功。具体毫秒数受机器调度影响，问题是健康检查也随写锁等待。
- 原因：`async def` 处理函数直接调用同步 repository；`sqlite3` 等待锁时阻塞其所在事件循环线程，当前 busy timeout 为 10 秒。
- 最小修复方向：把纯同步数据库业务路由改为普通 `def`，让框架在线程池执行；需要异步入口时，将完整同步业务操作移到线程池。连接仍在该业务操作内创建并关闭，不跨线程共享事务连接。
- 验收：保持写锁时，健康检查和无关请求仍能及时响应；另测并发写入错误与事务一致性。无需为了这一点更换数据库或一次性改成异步 ORM。

## 奥卡姆剃刀与代码质量

奥卡姆剃刀用于本项目的实际标准是：以尽可能少的概念和依赖，完整表达当前业务规则。必要的事务、权限、幂等、迁移和回收站校验都应保留，不能为了减少行数删掉。

| 方面 | 判断 | 最小行动 |
| --- | --- | --- |
| FastAPI + React/Vite + SQLite | 符合当前本机/小规模部署目标；没有多余的分布式组件 | 保留技术栈；多实例能力按真实需求评估 |
| 地块与茬次模型 | 实体数来自真实业务，不是过度抽象 | 保持作物单一来源；修正关联变更不变量 |
| 数据访问层 | SQL 直接、透明，但事务按函数分散提交，部分用例跨事务 | 先按业务原子操作划定事务，再考虑文件拆分 |
| 前端状态 | App 531 行、LedgerWorkspace 715 行；表单、列表、弹窗及跨入口协调集中 | 优先提取认证会话逻辑、LedgerForm 和 LedgerList；按职责拆分，不按任意行数拆分 |
| 依赖声明 | SQLAlchemy、Alembic、psycopg、redis 在当前 backend Python 中无接入，架构文档也明确闲置 | 核对脚本/发布入口后移除不用的运行依赖；不要为使用已有依赖而增加架构 |
| 层间依赖 | 普通业务走 service，账号、演示和回收站部分路由直达 repository；数据层也抛 HTTP 异常 | 明确业务不变量与事务的拥有者；薄查询不必强加一层透传 service |
| 模块关系 | repositories 局部导入 repositories_trash，后者又导入 repositories.now_utc | 小范围提取公共时间工具或调整调用方向，消除互相依赖 |
| 配置与版本 | REQUEST_TIMEOUT_SECONDS 被解析、展示，但未见实际请求超时执行；后端核心依赖没有可安装锁定约束 | 删除无效配置或落实其定义；提供可复现的部署约束与受控升级流程 |

`repositories.py` 1057 行、`styles.css` 1245 行本身不是缺陷，不能按长度机械重构。但账号、建议历史、地块、茬次、台账、待办、核算共处一个 repository 文件，已经增加定位成本。若后续持续开发，可按业务职责逐步拆分，并保留共享 SQL 条件，避免为了拆分复制统计/导出/列表逻辑。

当前多处 Hook 手工处理账户隔离、刷新、错误和加载状态，F2 说明保护策略依赖逐处记忆。先建立一个可靠的会话边界和请求版本规则；是否引入状态/查询库，应看拆分后是否仍存在大量实质重复，不必预先引入。

后端没有静态类型门禁，较多 `dict` / `Any`，前后端数据结构也需要手工同步。这属于维护成本，而非已经证明的运行故障。优先给跨层输入输出补明确类型，在现有模块逐步检查，不以引入大型代码生成工程为第一步。

## 修复顺序与范围

1. 先修 F1、F2：建立可靠的退出确认和会话轮次边界。
2. 修 F3、F4、F5：让建议对应输入、创建对应一个事务、茬次修改遵守已有台账约束。
3. 修 F6：隔离同步阻塞业务，验证并发请求响应能力。
4. 在上述问题的修改范围内做必要的小拆分；随后精简闲置依赖和无效配置，建立部署约束文件。
5. 用新回归用例重跑完整测试，再评估是否冻结交付版本。

这轮不建议扩展新功能、引入微服务、Redis、任务队列、通用仓储框架或更换数据库。先消除已证实的错误状态，让现有业务闭环稳定运行。
