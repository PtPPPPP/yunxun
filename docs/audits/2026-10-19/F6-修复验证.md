# F6 修复与验证

日期：2026-10-19。保留原审计报告与 F1–F5 的工作区修改；未提交、推送或部署。

## 实现

- `api/routes/auth.py`、`farm.py`、`tools.py` 的同步业务路由改为普通 `def`，由 FastAPI/Starlette 在线程池执行数据库访问、密码计算和完整事务。`system.py` 的数据库就绪检查及其他同步路由同样调整。
- `/health/live` 只访问内存配置和 ContextVar，继续异步执行。保留原有异步中间件及异常处理；没有需要在异步业务路由内拆分移交的 SQLite 操作。
- `core/database.py` 恢复 SQLite 默认的同线程校验。连接在同步业务函数内部创建、使用、提交/回滚和关闭；认证依赖只传用户字典，不传连接。
- 并发同名注册可能同时通过用户名预检；`repositories.create_user` 精确捕获用户名唯一约束冲突，返回 409，其他数据库错误继续上抛并回滚。
- 复查共享状态：限流器已有 RLock 保护检查/清理/重置/快照，配置为缓存的不可变 Settings，请求 ID 使用 ContextVar，未增加共享连接或全局业务锁。原有凭据变更、演示加载、回收站及 F4/F5 业务事务继续使用写锁下最终校验。

没有调整生产 worker 数、数据库类型、Schema、busy timeout 或依赖；没有引入异步 ORM。Cookie、CSRF、权限、限流、安全响应头和日志行为由回归验证。

## 真实服务并发回归

新增 `backend/tests/test_service_concurrency.py`，6 条测试均通过。测试在临时数据库上启动单 worker Uvicorn，服务运行于独立事件循环线程，客户端通过真实 TCP/HTTP 请求，不使用 TestClient 或 ASGI transport。

1. 独立连接执行 `BEGIN IMMEDIATE` 持有写锁；SQLite trace 发出信号，确认新增地块请求已进入 BEGIN。锁仍持有、写请求 Future 未完成时，`/health/live` 必须完成；随后再次确认锁和未完成状态，才释放锁。最后验证地块和第一茬完整提交。
2. 同样等锁，释放后通过临时库触发器使第二次 INSERT 失败，验证 HTTP 500 且地块/茬次均未残留。记录每个连接的创建、执行、提交或回滚及关闭，验证全生命周期处于同一业务线程，未在事件循环线程执行。
3. Event 暂停真实密码散列调用前的业务单元，验证存活检查先完成；释放后继续原始密码散列并成功注册，核对执行线程和请求 ID。
4. Barrier 确保两次同名注册均通过预检，验证最终一条 200、一条 409，数据库仅一个用户及一条新会话。
5. 8 个并发认证请求共享限流桶，额度 3 时精确得到 3 条 401、5 条 429，保留 Retry-After、安全头和各自请求 ID。
6. 6 个并发地块写入各有第一茬，业务日志中的 plot_id/user_id/request_id 与各自响应对应；同时验证 Cookie/CSRF、CORS 拒绝响应和另一账号的对象权限。

同步依靠 Event/Barrier/SQLite trace；信号与 HTTP 超时为 5 秒，释放和线程结束等待有上限。不使用 sleep 构造竞争窗口，也不比较脆弱的毫秒耗时阈值。

另在独立测试进程中仅将新增地块处理函数包装回旧的异步阻塞执行方式（未修改源码），运行相同写锁测试，按预期捕获 `httpx.ReadTimeout`。说明该测试能检出原问题；恢复后的正式代码通过全部测试。
